# Log signatures: from a pasted line to the owning file in one command

## Scope

The report usually arrives as a wall of log text with `path:line` suffixes from the reporter's own
install. Those suffixes are the cheapest routing evidence in the whole investigation, and guessing at
them is the most common way a run spends its output budget: one recorded triage burned 8.3 KB of
reasoning ranking which of five candidate lines produced `Aborted request` before issuing the single
`git grep` that answered it. Look the string up instead of reasoning about it.

Method: take the exact message text (not the reporter's file name — releases rename modules), then
`git grep -n '<message>' <ref> -- <dir>`. One call, and the answer is the file at the ref that ran.
Add the pattern to the table below when it settles a class.

Two exceptions, both recorded, and both cheaper than the grep:

- **A `[<file>.py:<line>]` suffix from vllm-ascend's own logger beats the message.** The line number is
  exact even when the paste has corrupted letters, so read that file at that line at the ref:
  `git show <ref>:<path> | nl -ba | sed -n '<line-1>,<line+4>p'`. `Loading draftter model..` under
  `[model_runner_v1.py:3686]` is `logger.info("Loading drafter model...")` at `v0.23.0rc1`, while a verbatim
  grep of the misspelt text finds it in neither repo — concluding "that string exists in no release" from
  the misspelling sends the search to the wrong clone (#12891).
- **A paste that mixes `1`/`l` is corrupted, not a fork.** One body's frames read
  `/v1llm-workspace/vllm/v1lvm/v1engine/core.py`, `DPEngineProc(crme,*args, *kwargs)` and `super()___init_`:
  it is an image/OCR transcription of `/vllm-workspace/…`. Grep a short stable prefix (`Loading draft`,
  `wait_for_ready`, `No available memory`), never the sentence, and do not treat a "string that does not
  exist" as a vendor fork.

## Rules

- **A `path:line` in the reporter's log is a claim about their build.** If the module they name does
  not contain that log call at the tag you pinned, the version is wrong (image tag vs `collect_env`,
  or a development build): fingerprint the ref from the line before analysing anything
  (`../workflow/version-pinning.md`).
- **A frame that is always there is not a finding.** Check whether the frame is a wrapper that wraps every
  call at that tag before reasoning from its presence. Example: `online_quantization.py:173
  patched_model_load_weights` looks like evidence of an online quantiser, but at vLLM `v0.13.0` it is the
  decorator on `AutoWeightsLoader.load_weights` (`models/utils.py:321`) and appears in *every* load; the
  quantisation question is answered instead by the logged args, the missing/allocated parameter names and the
  `Unknown quantization method` / `Cannot find the config file for <method>` guards
  (`../symptoms/quantization-load.md` §3).
- Add the row only when the grep at the ref settled it. A message that every release re-words
  ("Aborted request" survives, "Added request" is version-dependent) is not a stable route.
- The table is deliberately short: prefer a verified row over a plausible one, and record the ref the
  row was verified at next to it.
- **The deepest frame can be teardown.** A raise that is gated on a shutdown/cancel flag (`if
  self.shutting_down: raise …`, a `finally` that decrements a slot, a `cancel()` in a reader) fires
  *because* another process already died or was stopped; its message describes the shutdown, not the
  fault. When the deepest `vllm_ascend/` frame is such a line, the answer comes from the same run's
  worker/CANN log, and a report whose paste ends at that frame has no cause in it yet — say so
  instead of deriving one from the patch's own text.
