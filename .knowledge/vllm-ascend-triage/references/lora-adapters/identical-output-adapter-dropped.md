# Adapter output identical to the base model (a silently dropped adapter)

## Scope

A `--enable-lora` / `--lora-modules` serve starts clean, the adapter is listed, there is
no warning and no traceback — and the same body sent to `model=<adapter>` and
`model=<base>` comes back with the same text: "the responses generated by the LoRA model
and the base model are identical", "LoRA 不生效", "效果和 base 一样". Recorded #3668
(vllm-ascend `v0.11.0rc0` @ `00ba071`, Qwen1.5-4B-Chat, `--max-lora-rank 64
--max-loras 1 --max-cpu-loras 100`; reporter-confirmed fix = `--dtype`).

Every other shape in `index.md` carries a signature — a crash, a rate, an
`AttributeError`, a filtered ViT module, a named gate exception. This one carries
**none**, so the question is which silently-failing gate swallowed the adapter. There
are three; check them in this order, and say which rung produced the answer.

## Step 1 — the dtype half of the backend contract, before any graph theory

On everything but 310P the LoRA math never reaches stock vLLM's punica ops:
`vllm_ascend/platform.py:335-336` returns `vllm_ascend.lora.punica_npu.PunicaWrapperNPU`,
and that module's import is a bare `is_310p()` branch — 310P gets
`vllm.lora.ops.torch_ops`, every other SoC gets the AscendC kernels through
`vllm_ascend/lora/lora_ops.py` → `torch.ops._C_ascend.{bgmv,sgmv}_*`
(`punica_npu.py:9-16`; `lora_ops.py:24,38,55,72,87,110`).

Those kernels declare their dtype branches at **compile time** and their dispatch has an
empty fall-through. Verified at v0.11.0rc0:

| anchor | what it says |
|---|---|
| `csrc/kernels/bgmv_shrink.cpp:228-231` | `BGMV_SHRINK_TYPE_DECLARE(half)` always; `bfloat16_t` only under `#if (__CCE_AICORE__ >= 220)`. Same shape in `bgmv_expand.cpp:345,359`, `sgmv_shrink.cpp:245,263`, `sgmv_expand.cpp:360,378` |
| `csrc/kernels/bgmv_shrink.cpp:239-249` | `FP16` launches; `BF16` launches **inside that same `#if`**; `else { return; }` — the destination `y` is never written |
| `csrc/torch_binding.cpp:214-216` | the boundary check accepts exactly `kHalf` / `kBFloat16` (`"only support half and bf16"`) and rejects everything else |

So on a build whose `__CCE_AICORE__ < 220` the bf16 branch compiles to nothing while the
binding still accepts a bf16 tensor: the impl returns with `y` untouched, the layer emits
its pure base-layer output, and there is **no exception and no log line**. fp32 cannot
fail this way — it trips the `TORCH_CHECK` and is loud. That is the only mechanism that
matches the report exactly (fluent base-quality answers, clean log), and its lever is one
flag: `--dtype float16`. Reporter-confirmed on #3668: after a `--dtype` change the
adapter produced its own answers with the serve command otherwise unchanged; the recorded
run never got which value they passed, so ask.

Ask for the checkpoint's `config.json` `torch_dtype` — with `--dtype auto` the engine
follows it, and a bf16 checkpoint is exactly the case this hole needs. Label the
mechanism precisely: the code path is source-verified; whether *their* wheel compiled the
bf16 branch is the build's `__CCE_AICORE__`, which no export carries (`npu-smi info` SoC
plus the image tag is the nearest artefact).

## Step 2 — if the dtype is already `float16`, the next silent gate is module replacement

An adapter is applied by replacing linear modules with `*WithLoRA` wrappers, and the match
is **exact type identity**, never `isinstance`: `vllm_ascend/lora/utils.py:33,47,60,73`
(`type(source_layer) is AscendColumnParallelLinear`, …) next to upstream's
`type(source_layer) is ColumnParallelLinear`
(`vllm/lora/layers/column_parallel_linear.py:163`). The Ascend variants exist only after
`refresh_all_lora_classes()` runs, called from `PunicaWrapperNPU.__init__`
(`punica_npu.py:35`), and the classes they name are the ones the `CustomOp` registry swaps
in (`vllm_ascend/utils.py:523-540`, `REGISTERED_ASCEND_OPS`). A projection that is neither
the plain upstream class nor a registered Ascend class is silently not wrapped: adapter
weights load, nothing is applied, output equals base. So before any numerics story, put
the model's projections against that registry.

## Step 3 — graph mode is the second rung, and the pin's coverage explains why it tempts

At v0.11.0rc0 the guide advertises the pair — `docs/source/user_guide/feature_guide/lora.md:8`
("You can run LoRA with ACLGraph mode now"), `:11` ("enables the ACLGraph mode as
default") — while the tree's **only** LoRA e2e cases are eager and fp16:
`tests/e2e/singlecard/test_ilama_lora.py:50,54` and
`tests/e2e/multicard/test_ilama_lora_tp2.py:14,19` pass `dtype="half"` and
`enforce_eager=True`. Two consequences: nothing in CI compares adapter output against the
base model, so a dropped adapter passes; and "the graph path is unvalidated with adapters"
is a real hypothesis, so `--enforce-eager` is a legitimate rung. It is not rung 1 — #3668's
first answer ranked the graph lane first and the reporter's `--dtype` reply refuted it, so
run the dtype rung first and name which one the response is testing.

## Step 4 — ladder

| Rung | Action | What it proves |
|---|---|---|
| 0 | the same body with `temperature: 0` to `model=<adapter>` and `model=<base>` | the symptom is real, not a client cache or two different prompts |
| 1 | `--dtype float16`, plus the checkpoint's `config.json` `torch_dtype` | the AscendC kernel dtype branch (step 1) |
| 2 | `--enforce-eager` | the graph lane (step 3) |
| 3 | `--max-lora-rank` against the adapter's own `adapter_config.json` `r` | at v0.11.0rc0 the backend predicate is `is_310p()` only (`punica_npu.py:9`), so `--max-lora-rank 64` is innocent here; the "`max_lora_rank >= 128` demotes to torch_ops" rule is a **later** ref — do not read it onto this one |
| 4 | `target_modules` in the adapter against the model's module names | a name mismatch skips modules silently, the same defect class as step 2 |

Send back: `config.json` `torch_dtype`, the serve line's `--dtype` / `--max-lora-rank`,
both response bodies for one prompt, `adapter_config.json` (`r`, `target_modules`), and
the serve log's `Using PunicaWrapperNPU.` line.
