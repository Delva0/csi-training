# A feature upstream vLLM has and the Ascend fork has not plumbed

## Scope

A crash on the **first request** (or at engine init) whose exception is a plain Python type error on a
field or dict key — `TypeError: object of type 'NoneType' has no len()`, `AttributeError: 'NoneType'
object has no attribute …`, `KeyError: '<field>'` — raised in a file that vllm-ascend keeps as its **own
copy of an upstream file** (`worker/model_runner_v1.py`, `worker/npu_input_batch.py`, `worker/worker_v1.py`,
`core/scheduler.py`). The input the client sent is supported by upstream vLLM; the fork's copy of the
dataclass predates that support, so the field is absent and the first read of it raises. Worked member:
**prompt embeddings** (`prompt_embeds`, `--enable-prompt-embeds`, #4505). The deliverable is asymmetric:
a **mechanism with two verified code shapes** plus either an upgrade tag or "no server-side workaround
exists".

Not this page: a `transformers` model-type floor (`model-type-support-floor.md`), a renamed/removed
`additional_config` key that is silently ignored (`../vllm-ascend/config-flag-lifetimes.md`), or a
quantisation description mismatch (`quantization-load.md`).

## Common rules

- **Diff the two copies at the same version, don't reason about the API.** The fork's file is the
  evidence: `git show <ascend-tag>:vllm_ascend/worker/npu_input_batch.py | sed -n '/class
  CachedRequestState/,/def num_tokens/p'` beside `git show <vllm-tag>:vllm/v1/worker/gpu_input_batch.py`
  (or wherever the class moved) at the paired vLLM tag.
- **`git grep` for the feature at the reporter's tag is the first fact; an empty result is the class.**
  `git grep -c prompt_embeds <tag> -- vllm_ascend` → no output means the fork has no field by that name
  at all, which is exactly why the first request raises rather than misbehaving. The two halves to quote
  are the **dataclass field** and the **`num_prompt_tokens` derivation**.
- **Status is an ancestry question, not a HEAD-reading question.** One grep of `HEAD` cannot separate
  "added and later removed" from "never added", and it yields no release to recommend. Three commands,
  in this order:

  ```bash
  git -C /workspace/repos/vllm-project/vllm-ascend log --oneline --reverse -S'prompt_embeds' --all -- vllm_ascend/worker/model_runner_v1.py | head -3
  git -C /workspace/repos/vllm-project/vllm-ascend tag --contains <sha> | sort -V | head -3
  git -C /workspace/repos/vllm-project/vllm-ascend merge-base --is-ancestor <sha> <reported-tag> && echo in-tag || echo absent
  ```

  `--reverse` names the *introducing* commit (the fix for a missing feature), and `tag --contains`
  converts it into "fixed in vX". A recorded run spent four batches probing `HEAD`'s code instead and
  still could not say whether the feature existed anywhere.
- **Do not invent a workaround that the upstream input validation forbids.** Check the input layer
  before proposing "send both": `vllm/inputs/data.py is_tokens_prompt` / `is_embeds_prompt` require the
  two keys to be mutually exclusive, and `v1/engine/processor.py` sets `prompt_token_ids = None` whenever
  `type == "embeds"`. A workaround that needs both is impossible; say so.
- **The lever is a version or a different deployment, not a flag**, unless the feature has its own
  config switch (`--enable-prompt-embeds` is `ModelConfig.enable_prompt_embeds`, default False, and it
  is required for non-multimodal models — a client that sends embeds without it fails earlier).

## The signature

```text
(EngineCore_DP0 pid=…) TypeError: object of type 'NoneType' has no len()
  vllm_ascend/worker/model_runner_v1.py:650 in _update_states   → CachedRequestState(...)
  vllm_ascend/worker/npu_input_batch.py:70  in __post_init__    → self.num_prompt_tokens = len(self.prompt_token_ids)
```

The `<string>` frames between them are the dataclass `__init__` generated by `@dataclass`; read them as
the constructor, not as a lost source file.

## Mechanism: compare the same dataclass at both tags

- **Downstream (`vllm_ascend/worker/npu_input_batch.py` at `v0.11.0rc2`)**: `CachedRequestState` (`:46`)
  declares `prompt_token_ids: list[int]` (not Optional) and **no** `prompt_embeds` field, and
  `__post_init__` (`:70`) is literally `self.num_prompt_tokens = len(self.prompt_token_ids)`;
  `model_runner_v1.py:650-660` builds it with `prompt_token_ids=new_req_data.prompt_token_ids` and
  nothing else. `git grep -n prompt_embeds v0.11.0rc2 -- vllm_ascend` returns **no hits**, so the whole
  package lacks the path (verified, not inferred).
- **Upstream (`vllm/v1/worker/gpu_input_batch.py` at `v0.11.0`)**: the same class carries
  `prompt_embeds: Optional[torch.Tensor] = None` and computes
  `num_prompt_tokens = length_from_prompt_token_ids_or_embeds(self.prompt_token_ids, self.prompt_embeds)`;
  `gpu_model_runner.py:593` passes `prompt_embeds=new_req_data.prompt_embeds` and the prefill path is
  gated by `self.enable_prompt_embeds` (`:212`, `:841`/`:869`/`:885`, `:986`).
- So the crash is the fork's stale copy, not the engine: the engine legitimately hands
  `prompt_token_ids=None` for an embeds request (`vllm/v1/engine/processor.py:399-403`), and the fork
  dereferences it.

## Why there is no server-side workaround

`is_tokens_prompt` requires `prompt_token_ids` present **and** `prompt_embeds` absent, and
`is_embeds_prompt` requires the reverse (`vllm/inputs/data.py:136-144` at `v0.11.0`), and the processor
forces `prompt_token_ids = None` for `type == "embeds"`. "Send dummy token ids alongside the embeds" is
therefore impossible at the API level — do not propose it (one recorded run spent four batches checking
exactly this). The only levers are: send text and let vLLM tokenize (loses whatever produced the
embeddings), or move to a release that contains the support.

## Worked case: #4505 (`v0.11.0rc2`, prompt_embeds)

Reported: `0.11.0rc2` image, first `curl`/`generate` with `prompt_embeds` input; one comment only
(「这个我们后续有计划支持吗」), no maintainer answer. Thread **closed 2025-12-09** (created 2025-11-27) with
no stated reason — the plumbing commit below is the nearest resolution the history offers.

```text

    self.requests[req_id] = CachedRequestState(

```

- At `v0.11.0rc2` the fork's `CachedRequestState` has no `prompt_embeds` and `git grep prompt_embeds
  v0.11.0rc2 -- vllm_ascend` is empty. `[verified]`
- Upstream `v0.11.0` already supports the input: the field plus
  `length_from_prompt_token_ids_or_embeds` (`vllm/utils/__init__.py:3509`), `gpu_model_runner.py:593`
  passing it, and `self.enable_prompt_embeds` (`vllm/config/model.py:208`). `[verified]`
- **Fixed in `v0.12.0rc1`**: `216fc0e8e` ([feature] Prompt Embeddings Support for v1 Engine, #3026,
  2025-10-30) adds the field and the derivation and wires the runner. At `v0.12.0rc1`:
  `npu_input_batch.py:69` `prompt_embeds: Optional[torch.Tensor] = None`, `:73-75`
  `length_from_prompt_token_ids_or_embeds(...)`, `:155` `req_prompt_embeds`, `model_runner_v1.py:247`
  `self.enable_prompt_embeds = self.model_config.enable_prompt_embeds` and the embed prefill at
  `:704-731`; the e2e test is `tests/e2e/singlecard/test_completion_with_prompt_embeds.py:57`
  (`enable_prompt_embeds=True`). `merge-base --is-ancestor 216fc0e8e v0.11.0rc2` → absent; first tag
  `v0.12.0rc1`. `[verified]`

Deliverable: workaround for the reporter's tag — send text prompts (the tokenizer path) or run the
embeds workload on a GPU/vLLM deployment; **upgrade to `v0.12.0rc1`+** and serve with
`--enable-prompt-embeds` (`vllm/engine/arg_utils.py:562`; `ModelConfig.enable_prompt_embeds`) is the fix.
vLLM **force-disables prefix caching** when both are requested and logs a warning
(`arg_utils.py:1551-1557`) — say that, because the reporter may be running with prefix caching today.
Cost: prompt-embedding mode reserves differently and loses prefix-cache reuse.

## The path-move trap (this is where a HEAD read goes wrong)

At HEAD the support is in `vllm_ascend/worker/v1/model_runner.py:1496-1520` (`if self.enable_prompt_embeds`
… `self.input_batch.req_prompt_embeds`) and `npu_input_batch.py:107` `req_prompt_embeds`, while
`CachedRequestState` is now imported from upstream (`patch/worker/patch_v1/patch_mamba_utils.py:24`).
Grepping the old `model_runner_v1.py` or `npu_input_batch.py` for the field at HEAD returns almost
nothing — that is a **moved path, not absence**; one recorded run nearly concluded "still unsupported at
HEAD" from exactly that grep. Grep the field name across `vllm_ascend/` (all subdirectories), not the file
name you knew at the old tag (`../workflow/version-pinning.md`).

## Falsifier and recheck conditions

If `git grep -c '<feature>' <reported-tag> -- vllm_ascend` is non-zero, this page is the wrong class:
the field exists and the crash is a shape/plumbing bug inside vllm-ascend. The fork's file layout moves
(`worker/npu_input_batch.py` → `worker/v1/...` on later tags, `CachedRequestState` relocated), so re-grep
the class name at the reported ref before quoting a line number.
