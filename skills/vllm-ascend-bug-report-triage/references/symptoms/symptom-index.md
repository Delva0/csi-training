## Caveats that decide "new bug or not"

- HDK/CANN generation matters: #15896 is an HDK 25.1 hang; #16952 scopes the AICPU conflict to
  "HDK 0.26.0 or earlier". When the report gives a driver/HDK version, quote it.
- A CANN/torch_npu generation decides several classes: the `torch.version.cann.startswith("8.3")`
  test selects the compressed mask in v0.11.x (`attention-mask/`), and 310P's
  `hasattr(torch_npu, "_npu_flash_attention_v3")` gate. A reporter's `collect_env` CANN line is
  therefore load-bearing evidence, not decoration.
- Pooling (`MemCache`/AscendStore), KV offload, PP, DCP and sparse C8 interact in pairs; a report
  that changes two of them at once needs the pair named explicitly in the mechanism.
- A log line can be *cosmetic*: the "Unknown vLLM environment variable" warning fires for every
  `VLLM_ASCEND_*` name on pre-platform-hook releases. Do not "fix" a working configuration because of
  it, and do not read a warning as evidence that the variable was ignored.
- A device DFX kernel name/hash is CANN scope: the Python only chooses the layout and the operator, so
  the fix lands in a CANN release. Name both halves rather than filing it as a vllm-ascend defect
  (`device-kernel-faults.md`).
- `release_notes.md` `Known Issues` entries are version-scoped prose ("In v0.23.0, ..."). Check
  which `## vX.Y.Z` heading the line sits under before applying it to the reporter's build.
- Machine-level mismatch: an issue on `v0.18.0rc1` reported `torch_npu==2.9.0.post1+gitee7ba04`, a
  build the tag does not pin. Operator availability follows the installed torch_npu/CANN, so a
  `hasattr(torch_npu, ...)` gate can differ between two users of one vllm-ascend release.
- Reverted fixes are not resolutions — check before citing one (`../workflow/fix-discovery.md`).
- A `call aclnn<Op> failed … Parse dynamic kernel config fail … AclOpKernelInit failed opType` pair is
  the image's CANN base being another SoC's build (`910b` on a 910C/A3 card), not a model or flag problem:
  `Dockerfile.a3` first exists at `v0.10.0rc1`, `Dockerfile.a5` at `v0.23.0` (`device-kernel-faults.md`,
  `../vllm-ascend/install-and-image.md` §1).
- Wrong output on the **first** call only, with `enable_sleep_mode=True` and no `sleep()` call, is an
  allocator-path class: `enable_sleep_mode` is the trigger, the graph mode only decides crash-vs-garbage
  (`sleep-mode-and-allocator.md`).
- A transport failure belongs to the environment until a host-plane address is the failing one: a device-plane `ip[192.168.*]` in the plog is the NPU's RoCE address, not `HCCL_IF_IP`, and no `vllm_ascend/` line sits in that chain (`../hccl/index.md`).
- A request that never runs and then blocks everything behind it is admission, not a collective: blocks
  (pool × smallest `block_size`) against `max_admission_blocks_per_request`, and `--max-num-batched-tokens`
  moves the cliff (`kv-admission-cliff.md`).
