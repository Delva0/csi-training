# Fixed wrapper text, and the owner behind it

Scope: a paste whose decisive line is a sentence the code prints unconditionally — canned
advice inside an `except`, a recommendation, a deprecation notice, an import warning made
by a placeholder module, or a `/health` 200 — so the wording names a cause the code never
checked. Read this page when rule 11 of SKILL.md applies: before adopting a log's own
explanation, before ranking an op named by such a line, and before treating health as
liveness. The per-lane mechanisms stay in the pages each section links; this page is the
inventory and the test that separates the wrapper from the owner.

## Classify the appended error, not the wrapper

vllm-ascend logs canned advice inside `except` blocks and re-raises, so the sentence names a cause the code never checked — the `ACLgraph has insufficient available streams … Recommended solutions` block prints for *any* capture exception (`model_runner_v1.py:3553-3565` at v0.11.0rc0, `:3143-3152` retCode-gated at v0.12.0rc1, absent at v0.18.0rc1, back `207008`-gated by v0.21+: re-grep per version) — so **classify the appended error, not the wrapper**: Step 2 of `references/startup-failures/acl-graph-capture.md` sends a collective/transport code (`EI0006 … Remote Rank did not send the data in time` inside an `HcclAllreduce`, the `[Create][DestLink]Create Dest error!` beside it), a plain Python exception, a synchronize refusal (`107027`), a capture-mode copy (`107030`) and an aclop refusal each to its own page, while `capture-stream-table-exhaustion.md`'s stream arithmetic applies only when that inner line is the capture-begin resource refusal (`207005` / `Alloc sq cq fail` / `stream_id=…`). Its "Recommended solution 2" is a lever a pooling serve refuses, so price a logged recommendation against the engine's own gates before repeating it (`references/startup-failures/capture-stream-table-exhaustion.md` §4). Before adopting a log's own explanation, `rg -n '<fragment>' vllm_ascend/` — and in the upstream `vllm/` tree when that comes back empty, since a message naming triton/torch internals is usually upstream's: `Failed to import Triton kernels … please make sure your triton version is compatible` is vllm's `logger.error` around an optional `triton_kernels` import, so its advice names the action the reporter already tried and the crash is elsewhere (`references/image-dependency-faults/triton-kernels-import-error.md`) — and read the emitting site: an `except Exception` that appends `{str(e)}` and re-raises carries the inner error as evidence, not the wrapper. Same family as procedure step 3's sync-point trap: where an error surfaced is not necessarily its owner.

## Import warnings, resource allocs and capture advice

**One member of the family is a warning that names a harmless feature**: `Failed to import vllm_ascend_C:<tail>. Sleep mode will be disabled.` reads as a sleep-mode notice, but an extension that never imported registers **no** `_C_ascend` op, so the `AttributeError: '_OpNamespace' '_C_ascend' object has no attribute '<op>'` that follows — at a request *or* in the memory-profiling dummy run — names whichever op was reached first, never an unsupported one (#3342/#3090 `weak_ref_tensor`, #6527 `moe_gating_top_k`). Read that warning's **tail** before ranking the op: `No module named …` = no `.so` in the image, `: undefined symbol: …` = present and refused by a SoC source-list gate (`references/image-dependency-faults/custom-op-extension-missing-from-image.md`, Step 0). CANN prints the same kind of wrapper under the code: `[Error]: Failed to apply for memory.` / `Check the remaining storage space in the hardware environment` + `EL0006 … resources are insufficient` is the canned text of a *resource-alloc* refusal (`207005`), so read the `[SqCqManage]Alloc sq cq fail …` line under it before treating such a paste as an HBM, disk or container-size report (`references/startup-failures/capture-stream-table-exhaustion.md`).

The rule covers *advice* too: `Cannot run aclop operators during NPU graph capture … please try to set torch.npu.config.allow_internal_format = False` is torch_npu's capture guard quoting a suggestion, and vllm-ascend assigns that option `True` at import (`worker/model_runner_v1.py:138` at v0.11.0rc0, `:154` at v0.18.0rc1), so it cannot be applied from the launch shell; the op named in the message is the subject and the FX trace beside it names the owner (`references/startup-failures/aclop-op-during-graph-capture.md`).

## The multiproc wrapper, and the quant lanes that start from it

The same rule covers the multiproc wrapper, in the one direction that changes what you ask for: `WorkerProc failed to start.` is `logger.exception` (`vllm/v1/executor/multiproc_executor.py:749` at vllm v0.14.1), so the rank's whole stack is printed **below** it, every line under that same `[multiproc_executor.py:749]` prefix — ask for the block below the line, not above it. When the paste cannot carry that block at all (a screenshot whose `*.ocr.txt` is noise, a title-only report), the wrapper is all the evidence there is: classify from the serve path's own tokens — a quant variant in the model directory (`…-W8A8`, `…-w8a8_dynamic`) decides the lane — and put the traceback request in the answer. Two quant lanes start there, and the launch line separates them before any page read: **no** `--quantization ascend` / `quantization="ascend"` anywhere in the command is the gate that never fires (the msmodelslim export's `config.json` carries no `quantization_config` on purpose, so upstream's auto-detect cannot fire and a dense engine meets int8 tensors — the quant gate's §B (`references/startup-failures/quantization-method-gate.md`), recorded #2015, where the pin's `DeepSeek R1 ✅` row says nothing about it), while the aux-key family (`…weight_scale`, `w2_weight_offset` — `references/startup-failures/weight-scale-keyerror-quant-variant.md`) needs a traceback that names such a key. Reading `supported_models.md` first is the recorded detour: the flag, not the model row, is the discriminator.

## The oddest flag, and an env var that restates the default

**The oddest flag in the command is not a substitute**: `--mm_processor_cache_type shm` ranks only with its own `Data for address:id …` string. Recorded #7744 demoted that flag correctly and still led with the wrong lever — "the `--quantization ascend` flag is missing" — on a load-phase `KeyError: 'layers.37.mlp.experts.w2_weight_offset'`, while its resolution was the newer tag (reporter-confirmed `v0.17.0rc1`). So price a flag-omitted verdict against the model dir's own `quantization_config` first: the override only *renames* an existing `quant_method`, and the VL-MoE expert branch is still unguarded at v0.18.0, so a flag-omitted engine fails the same way on the newer tag (item 4 of `references/startup-failures/weight-scale-keyerror-quant-variant.md` §*The VL-MoE offset form*; `references/startup-failures/silent-worker-exit.md`). **Check a suspect env var against the pin's own default before calling it the reporter's knob** — `rg -n '<ENV>' vllm_ascend/envs.py` — because a launch line that restates the default carries no information about the fault (`VLLM_ASCEND_ENABLE_MLAPO=1` is the default at v0.14.0rc1 `envs.py:95-99` and v0.18.0rc1 `:82-86`, and the tutorials export the same), while `=0` on that key is still a legitimate one-launch ablation; recorded #7015 shipped "你自己加的非默认开关" for exactly that line (`references/hccl-and-hardware/mc2-dispatch-profile-run-hang.md`, refuted rows).

## A `/health` 200 is the same kind of wrapper

**A 200 from `/health` is the same kind of wrapper where it decides a verdict**: on vllm v0.23.0 the route reads frontend flags only — `errored` = `engine_dead or not is_running(output_handler)` (`async_llm.py:900-903,1045-1055` behind `health.py:30-34`) — while the executor's real `check_health` RPC (`multiproc_executor.py:491-493`) has **no caller** (`rg -n 'check_health' vllm/`) and could not be answered anyway (`worker_busy_loop` serves one RPC at a time, `:969-997`), so a worker blocked mid-step looks healthy for the RPC deadline. One grep settles it per pin (v0.18.0 `async_llm.py:874-877`; an older release does reach a 10 s probe, `rpc-watchdog-timeouts.md`); then say "health is not a liveness probe here" once, with the lines — not another poll, not a health-defect row: `references/scheduler-admission/background-helper-death-wedge.md` (#18691, a dead Dynamic-EPLB planner subprocess; its `platform.py:1275-1282` floor also makes a launch-side `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS=8` inert).
